## 1. Pay.sh mechanics

Pay.sh is two things that the press coverage blurs together: (a) the **`pay` CLI/wallet** (`solana-foundation/pay`) that any agent can wrap around any 402-speaking API, and (b) the **Google Cloud gateway** (proxy in front of BigQuery, Gemini, Vertex AI, Cloud Run + 50+ community APIs) announced with the Solana Foundation (launch 2026-05-05 per baseline §1; solana.com news page carries no explicit date — **M** on the date, **H** on the architecture). ([solana.com/news](https://solana.com/news/solana-foundation-launches-pay-sh-in-collaboration-with-google-cloud), read 2026-07-26)

**Request flow** (`solana-foundation/pay` README, read 2026-07-26, **H**): `pay` wraps a CLI or agent session (`pay --sandbox curl <url>`, `pay claude`, `pay codex`); when the API returns 402 it (1) detects the payment protocol from response headers, (2) prepares a stablecoin transaction locally, (3) requests wallet authorization with platform biometric gating (Touch ID / Windows Hello / GNOME Keyring), (4) retries the original request with payment proof. Ships a built-in MCP server (paid calls through the same local-approval flow) and an embedded Payment Debugger (public instance at debugger.pay.sh) that renders each 402 challenge-response cycle as a sequence diagram.

**Which parts speak x402 vs MPP** (**H** for the dual-protocol claim, **M** for the split): the `pay` client implements both **x402** (x402.org spec) and **MPP** — the Tempo Labs + Stripe "Machine Payments Protocol", i.e. the `Payment` HTTP authentication scheme, IETF-draft-tracked, full rendered spec at paymentauth.org ([github.com/tempoxyz/mpp-specs](https://github.com/tempoxyz/mpp-specs), read 2026-07-26). Protocol selection is per-response-header at step (1). x402 is exact per-request challenge/proof; MPP adds `WWW-Authenticate: Payment` / `Authorization: Payment` and, via per-rail **Session** drafts (EVM, Lightning, Solana, Tempo listed at paymentauth.org, **H** for existence, **L** for detail — the index page exposes titles only), escrow-deposit sessions with signed micropayment vouchers batch-settled at session close, unused funds refunded (secondary: formo.so MPP explainer, **M**; the Solana session spec is reportedly "SDK live, spec not yet finalized" — **L**). The pay.sh docs also reference "MPP subscription delegations" as a managed recurring-charge surface ([pay.sh/docs/using-pay](https://pay.sh/docs/using-pay), read 2026-07-27, **M** — overview page only).

**Settlement**: "Settlement happens in seconds. Payments are processed in stablecoins over Solana's high-throughput network, then reconciled with the provider" (solana.com news, **H** for the quote). PayAI is a launch partner; its facilitator exposes `/verify`, `/settle`, and a `/list` endpoint "to help clients discover merchants", free tier 10,000 settlements/month ([docs.payai.network/x402/facilitators/introduction](https://docs.payai.network/x402/facilitators/introduction), read 2026-07-27, **H**). PayAI network strings `solana` + `solana-devnet` come from the baseline (solana.com/x402, facilitator.payai.network, 2026-07-26, **M** — not re-confirmed on the introduction page read today). **Unknown**: whether the Google Cloud gateway settles exclusively through PayAI or multiple facilitators — not stated in any source read.

**Catalog structure and registration** (`solana-foundation/pay-skills`, read 2026-07-26, **H**): the catalog is a community git registry of `PAY.md` files at `providers/<operator>/<name>/PAY.md` (or `<operator>/<origin>/<name>/` for proxied APIs — e.g. `solana-foundation/google/translate`). Required frontmatter: `name`, `title`, `description` (64–255 chars, powers search), `use_case` (32–255 chars, "helps LLMs route requests"), `category` (17-value enum: `ai_ml`, `cloud`, `compute`, `data`, `devtools`, `finance`, `identity`, `maps`, `media`, `messaging`, `other`, `productivity`, `search`, `security`, `shopping`, `storage`, `translation`), `service_url` (production HTTPS), and one of `openapi: url|path` or inline `endpoints:`; optional `version`, `sandbox_service_url`. Registration: `pay catalog scaffold <fqn> <openapi_url>` → edit → `pay catalog check` (parses frontmatter, fetches OpenAPI, probes endpoints) → PR; CI blocks merge unless paid endpoints return a valid **Solana-mainnet 402 challenge accepting USDC or USDT**. Note: **pricing is not a frontmatter field** — price lives only in the live 402 challenge. (One WebFetch summary expanded MPP as "Metaplex Payment Protocol"; that contradicts the `pay` repo's own paymentauth.org reference and is treated as a summarization artifact — MPP here is Machine Payments Protocol.)

**Stablecoin support**: USDC/USDT on Solana mainnet enforced by catalog CI (**H**); the `pay` README says Solana-deployed stablecoins are supported "out of the box" (**H**); no evidence of AUDD or other non-USD stablecoins anywhere in the Pay.sh surface (consistent with baseline §2).

## 2. x402 V2 discovery metadata

Three distinct discovery surfaces exist in the x402 V2 world; they are related but not the same thing:

**(a) V2 Discovery extension** (x402.org/writing/x402-v2-launch, 2025-12-11, read 2026-07-26, **H**): V2 formalizes "Extensions" with lifecycle hooks; the Discovery extension lets facilitators "automatically index available endpoints" with pricing/metadata kept current from live traffic. The launch post gives no field names. Also relevant to Pay.sh session talk: V2 adds wallet-controlled sessions (SIWx header per CAIP-122, announced as fast-follow) and dynamic `payTo` routing.

**(b) Bazaar extension — the concrete declaration format** ([docs.x402.org/extensions/bazaar](https://docs.x402.org/extensions/bazaar), read 2026-07-27, **H**): extension key `"bazaar"` inside the route config / payment response `extensions` object. `extensions.bazaar.info.input` requires `type: "http"|"mcp"`; HTTP inputs carry `method` (+ optional `queryParams`), MCP inputs carry `toolName`, `inputSchema` (+ optional `description`, `transport`, `example`); optional `output` requires `type` (+ `example`, `schema`). Listing enrichment on the `resource` object: `serviceName` (≤32 ASCII), `tags` (≤5 × ≤32 chars), `iconUrl` (≤2048 chars) — individually soft-dropped on validation failure. The facilitator acknowledges cataloging via an `EXTENSION-RESPONSES` response header (base64 JSON, key `"bazaar"`, status `success|processing|rejected`).

**(c) CDP Bazaar list/search schema** ([docs.cdp.coinbase.com/x402/bazaar](https://docs.cdp.coinbase.com/x402/bazaar), read 2026-07-26, **H**): `GET /v2/x402/discovery/resources` (paginated, `limit`/`offset`), `GET /v2/x402/discovery/search` (semantic, quality-ranked), `GET /v2/x402/discovery/merchant?payTo=<address>`. Listing fields: `resource` (endpoint URL), `type` (`"http"`), `x402Version`, `accepts[]` (`scheme` — e.g. `"exact"`/`"upto"` — `network` (CAIP-2), `amount`, `asset`, `payTo`, optional `maxTimeoutSeconds`), `lastUpdated`, optional `metadata`, `curated`, `skillUrl` (hosted SKILL.md for curated entries). Indexing is settlement-gated: "There is no separate registration step. The CDP Facilitator catalogs your service the first time it settles a payment for that endpoint" — declaration via `bazaarResourceServerExtension` + `declareDiscoveryExtension()` plus **at least one successful settlement**.

**`.well-known/x402`**: community-documented as a self-hosted machine-readable manifest listing every resource with full payment requirements (price, networks, `payTo`) — seen in the xpaysh/awesome-x402 ecosystem, discoverx402, and A2A-adjacent stacks that expose `/.well-known/x402` beside `/.well-known/agent-card` (read 2026-07-26/27). **Caveat (M/L)**: I could not locate `.well-known/x402` in the official Bazaar docs (explicitly absent from the CDP page) or confirm a canonical schema in the x402-foundation spec repo during this sweep. Treat it as a real but **convention-stage** surface: self-asserted, unverified, no single normative schema confirmed. This matters for §5 — a pointer field must not pretend the target is a settled standard.

MPP has its own separate "Discovery" draft plus a "service directory" in the tempoxyz/mpp repo (**H** for existence, **L** for content — not readable in this sweep). Unknown: its relationship to `pay-skills`.

## 3. ADL v0.2 mapping table

ADL sources considered: `metadata.name`/`metadata.description`, `harness.tools` (function/mcp/http/native), `extensions.x402` (`enabled`, `intents[]` with `id`, `direction: spend|refund|charge`, `maxAmount`, `currency`, `rails`, `requireReceipt`, `policyRefs`, `purpose`, `scope`, `authority{principal, spender, maxAmount, currency, expiry, revocation}`; `policy{budgetPerTask, requireHumanApprovalAbove}`), `extensions.receipts`, `extensions.reputation` (specs/ADL-v0.2.md, specs/PAYMENT-REPUTATION-EXTENSION-v0.1.md).

**The cap-vs-price distinction governs every row**: ADL `maxAmount` (intent and authority) is a *buyer-side authorization ceiling* — "the harness may spend at most X". Every discovery surface instead carries a *seller-side quote* — "this call costs X" (`accepts[].amount`, the live 402 challenge, the `.well-known` manifest price). These are different speech acts by different parties; neither can be derived from the other. The only legitimate static relation is a **funding check**: quoted `amount` ≤ matching intent `maxAmount` with compatible `currency`/`asset` and `rails`/`network`. x402's `"upto"` scheme is the one place a seller quote is itself cap-shaped; even then it caps the charge, not the buyer's authority.

## 4. Divergences and risks

**MPP sessions vs ADL's exact-payment authority contract (H that the mismatch exists; M on session detail).** ADL v0.2 authority is per-intent and exact-shaped: one `maxAmount`, one `requireReceipt`, receipt bound to a task. An MPP session is a *cumulative* authorization: escrow deposit up front, N signed vouchers streamed against it, one batch settlement, remainder refunded. Nothing in ADL can express (a) a session-level cap distinct from per-request amounts, (b) voucher-granularity spend that never individually touches the chain, or (c) refund-of-remainder as a settlement outcome rather than a distinct `refund` intent. Until ADL grows a session-cap concept (baseline §1 verdict), any MPP mapping is **unsupported, not degraded** — a static checker must refuse it rather than approximate. Pay.sh "MPP subscription delegations" adds a recurring-charge variant with the same problem.

**Settlement-gated discovery vs report-only agents (H).** Bazaar indexing requires ≥1 real settlement. A ReddiAgent whose only rail is `x402-dry-run` can therefore **never appear in Bazaar** — listing is constitutively a live-payment act. Any "list our agents" ambition sits behind the RAP repo's live-rail gates, not this repo. Pay.sh's PAY.md catalog is friendlier: PR + CI probe, but CI still requires a live Solana-mainnet 402 challenge from `service_url`, so the same boundary holds.

**Trust-layer gap = RAP's opening (H, backed by peer review).** Pay.sh's full flow — 402 → sign → retry → response, facilitator `/settle`, provider reconciliation — proves *payment happened*, never that *the paid-for service was delivered as specified*. That is precisely the "paid-but-denied" failure demonstrated in the wild (arXiv 2605.11781) and the facilitator-integrity failures found in all 15 major x402 facilitators (arXiv 2607.19545, USENIX Sec 2026). On top of Pay.sh's flow, a RAP receipt layer would add: request/response hashes bound to the settlement reference and a single request ID (replay window, arXiv 2605.30998), eval-gated receipt emission, and capability-tagged reputation signals — none of which any of the four discovery surfaces carries (§3 last row). Pay.sh's Payment Debugger *visualizes* the cycle but attests nothing.

**Discovery integrity is soft (M).** `.well-known/x402` manifests are self-asserted with no verification story; Bazaar's own ack pipeline has documented flakiness (x402-foundation/x402#2112: facilitator never emits `EXTENSION-RESPONSES`, service silently not indexed). Quality signals live only in one vendor's ranking. Treat all catalog content as claims, not facts — another receipts-shaped gap.

**Naming/versioning risks (M).** "MPP" collides in the wild (one fetched summary mis-expanded it as Metaplex); x402 V2 explicitly moves behavior into SDK extensions, so the Bazaar field set can drift without a spec version bump — pin doc dates, not just `x402Version`.

## 5. Recommendation block

A future `scripts/paysh_discovery_compatibility.py` (separate code issue; this report is its spec) should be a **static checker with the MAF report contract** (`target: paysh-discovery`; `runtimeExecutionAllowed`/`networkAccess`/`paymentAccess`/`mcpInvocation` all false — it reads local ADL docs plus *locally supplied* catalog fixtures; it never fetches `service_url`, a `.well-known` manifest, or a facilitator endpoint):

1. **PAY.md synthesis check**: from an ADL doc, verify `name`/`title`/`description` derivable; enforce description 64–255 chars; emit loss codes `paysh-no-category-taxonomy`, `paysh-no-use-case-source`, `paysh-no-service-endpoint` for the three no-source fields.
2. **Bazaar declaration check**: derive `extensions.bazaar.info.input` stubs from `harness.tools` mcp entries (`toolName` yes; `inputSchema` omitted with loss code until #389 lands schemas); validate `serviceName` ≤32-ASCII derivation from `metadata.name`.
3. **Funding check (cap-vs-price)**: given a fixture `accepts[]` array, verify `amount` ≤ matching intent `maxAmount`, `asset`↔`currency` match via explicit table, `network`↔`rails` via explicit CAIP-2 vocabulary map; handle `exact` vs `upto` schemes; never emit "price" from ADL.
4. **Charge-side rigor**: if the ADL doc declares `charge` intents, require the full authority block even though v0.2 conformance doesn't (delegation-examples gap 1).
5. **Refusals**: MPP session/subscription fixtures → `unsupported: mpp-session-semantics`; any fixture implying live listing (settlement-gated Bazaar entry for a dry-run-only agent) → explicit boundary error, mirroring `a2a_agent_card_export_would_drop_reddi_semantics`.

**`.well-known/x402` in ADL v0.3 (#389): yes, as a pointer — with a hedge.** Adopt the baseline verdict: ADL should carry discovery *pointers* (`.well-known/x402` URL, Bazaar/registry resource refs, catalog FQNs like a pay-skills provider path), never an embedded price schema — price stays at the discovery surface, cap stays in ADL. Because the `.well-known` convention is not yet confirmed normative (§2 caveat), the v0.3 field should be shaped as a generic discovery-pointer list with a `kind` discriminator (`well-known-x402`, `bazaar`, `paysh-catalog`, `payai-list`) rather than hard-coding one convention.

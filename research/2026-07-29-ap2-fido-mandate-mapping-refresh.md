## 1. AP2 v0.2.0 mandate structure

Release facts: v0.2.0 shipped 2026-04-28 ("second release … focuses on providing Human Not Present flows", [github.com/google-agentic-commerce/AP2/releases](https://github.com/google-agentic-commerce/AP2/releases), read 2026-07-29, **H**) — the same day as the FIDO announcement, reading as a coordinated donation (**M** for coordination intent). v0.1.0 was 2025-09-16.

**Three surfaces are live, all reachable from the same release:** the prose spec, the machine-readable schemas plus the SDK generated from them, and a separate legacy models package.

**(a) Normative spec — Agent Authorization Framework + the two mandate pages.** Three deep links, each re-fetched HTTP 200 on 2026-07-30 (**H**): [/ap2/agent_authorization/](https://ap2-protocol.org/ap2/agent_authorization/) (109,621 bytes), [/ap2/checkout_mandate/](https://ap2-protocol.org/ap2/checkout_mandate/) (150,101 bytes), [/ap2/payment_mandate/](https://ap2-protocol.org/ap2/payment_mandate/) (149,048 bytes). Cite these, not the site root: a bare `/ap2/mandates/` path returns **404** (verified same session), so any citation of "the mandate pages" without a path is unreproducible. Two mandate families, each **open** (constraints set before finalization) or **closed** (a specific finalized transaction), as **SD-JWT VCs**:

- **Checkout Mandate** — `vct` `mandate.checkout.1` (closed) / `mandate.checkout.open.1` (open). Claims: `checkout_jwt` (base64url merchant-signed JWT of the checkout payload), `checkout_hash` (base64url hash of `checkout_jwt`, per `_sd_alg`, default SHA-256), optional `iat`/`exp`; `checkout_jwt`/`checkout_hash` are selectively disclosable. Open-mandate constraint types: `checkout.allowed_merchants`, `checkout.line_items` (maximal-flow quantity matching).
- **Payment Mandate** — `vct` `mandate.payment.1` / `mandate.payment.open.1`. Closed claims: `transaction_id` (hash of `checkout_jwt` — the checkout binding), `payee` (Merchant: `id`, `name`, `website`), `payment_amount` (`amount`, `currency`), `payment_instrument` (`id`, `type`, `description`), optional `pisp`, `execution_date`, `risk_data`, `iat`/`exp`. Open-mandate constraint types: `payment.agent_recurrence`, `payment.allowed_payees`, `payment.allowed_payment_instruments`, `payment.allowed_pisps`, `payment.amount_range`, `payment.budget` (total across recurrences), `payment.reference` (binds to an open Checkout Mandate via `conditional_transaction_id`), `payment.execution_date` (`not_before`/`not_after`).
- **Key binding**: `cnf` (JWK, RFC 7800) is "REQUIRED if the Mandate is still open" — the agent proves possession via a KB-JWT when closing/presenting after the user has left. Unknown constraint types "MUST be treated as failing evaluation" (fail-closed). Both quotes re-grepped on `/ap2/agent_authorization/` 2026-07-30 (1 hit each, **H**).
- **No revocation mechanism is specified.** Search scope, stated so the grade is auditable: tag-stripped case-insensitive grep of the three pages in (a) for `revocation`, `revoke`, and the stem `revok` returns **0 hits on all three**, plus **0 hits** across five machine-readable files in (b) — the four mandate schemas and `types/amount.json` (2026-07-30). **H** for the absence *within that scope* — it is not a claim about AP2 material outside those eight files.
- **Presentation**: OpenID4VP with a `transaction_data` entry whose `type` is, per the spec, "REQUIRED. MUST be the string value `delegate`" — written `type: "delegate"` (the earlier `_delegate_` rendering in draft notes was markdown italics around the value, not part of it; re-read on `/ap2/agent_authorization/` 2026-07-30, **H**). The entry carries `format`, `delegate_payload` (mandate contents), optional `delegate_disclosures`. The verifier returns a **Mandate Receipt** (signed JWT: `iss`, `result` `success|error`, `reference` = base64url hash of the received mandate, optional `error`/`error_description`); the Payment Receipt adds `status`, `payment_id`, optional `psp_confirmation_id`, `network_confirmation_id`. The spec notes ISO mDoc (18013-5/-7) could substitute for SD-JWT VC (**H**).

**(b) Machine-readable schemas + the generated SDK — this surface ships the v0.2 model, not the v0.1 trio** (all paths read via the GitHub raw/contents API 2026-07-30, **H**). `code/sdk/schemas/ap2/` holds `checkout_mandate.json`, `open_checkout_mandate.json`, `payment_mandate.json`, `open_payment_mandate.json` (plus `checkout_receipt.json`, `payment_receipt.json` and a `types/` directory: `amount`, `item`, `jwk`, `merchant`, `payment_instrument`, `pisp`, `receipt_status`), each `$id`-rooted at `https://ap2-protocol.org/schemas/…`. Required sets read directly from those files: closed checkout `[vct, checkout_jwt, checkout_hash]`; open checkout `[vct, constraints, cnf]`; closed payment `[vct, transaction_id, payee, payment_amount, payment_instrument]`; open payment `[vct, constraints, cnf]`; `exp` optional on all four. Two structural facts worth pinning: the open payment mandate's `constraints` array carries `"contains": {"$ref": "#/$defs/payment_reference"}`, so **every open Payment Mandate must include a `payment.reference` constraint** (JSON Schema default `minContains: 1`); and `payment.amount_range.max` is `type: integer` (minor units) while `payment.budget.max` is `type: number` — an inconsistency inside AP2's own schemas, reported here as read, not resolved. The same schemas are code-generated into `code/sdk/python/ap2/sdk/generated/` (codegen header on `payment_mandate.py`: `timestamp: 2026-04-28T00:39:38+00:00`, the v0.2.0 release day) and wired by `code/sdk/python/ap2/sdk/` — `mandate.py` (`MandateClient` create/present/verify), `sdjwt/`, `constraints.py`, `checkout_mandate_chain.py`, `payment_mandate_chain.py`, `receipt_wrapper.py`, `disclosure_metadata.py`.

**(c) Legacy models package (`code/sdk/python/ap2/models/mandate.py`, read via gh 2026-07-30, H)** — a package *separate from* `ap2.sdk`, still carrying the v0.1-era trio: `IntentMandate` (`user_cart_confirmation_required`, `natural_language_description`, `merchants`, `skus`, `requires_refundability`, `intent_expiry`), `CartMandate` (`contents`: `CartContents{id, user_cart_confirmation_required, payment_request, cart_expiry, merchant_name}`, `merchant_authorization` JWT with `cart_hash`/`jti`), `PaymentMandate` (`payment_mandate_contents{payment_mandate_id, payment_details_id, payment_details_total, payment_response, merchant_agent, timestamp}`, `user_authorization` — docstring: "base64url-encoded verifiable presentation of a verifiable credential signing over the cart_mandate and payment_mandate hashes … an sd-jwt-vc"). Naming caveat: "legacy" here is our dating, not an upstream label — `ap2/models/__init__.py` is a bare licence header and neither it nor `mandate.py` carries a deprecation marker (checked 2026-07-30), and a repo-wide code search for `legacy` returns three unrelated hits. So the Intent concept survives in this package as prose intent + expiry; in the v0.2 credential model of surfaces (a) and (b) the intent role is played by the **open** Checkout/Payment mandates' constraint arrays.

**Deltas vs the #133 baseline (explicit):**

1. The fixture mandate field set `id/vcRef/issuer/subject/scope/expiresAt/auditRef` (MANDATE_FIELDS in scripts/ap2_x402_mandate_report.py) matches **none of the three** surfaces above — it was a placeholder vocabulary. Real identification is by **hash** (`checkout_hash`, `transaction_id`, receipt `reference`), not an `id` claim; scope lives in typed `constraints`, not a prose `scope` string (**H**).
2. Fixture `PaymentMandate.settlementRail`, `.asset`, `.maxAmount`, `.revocationRef` do not exist in AP2: **AP2 carries no rail claim** (nearest is `payment_instrument.type`; rail/network is x402-side), amount ceilings are open-mandate constraints (`payment.amount_range`/`payment.budget`), and **no revocation path exists** (**H**).
3. Mandate topology changed: Intent/Cart/Payment trio (v0.1, surviving only in the legacy `ap2.models` package, surface (c)) → Checkout/Payment × open/closed (v0.2 spec *and* v0.2 schemas/SDK, surfaces (a) and (b)), with Cart renamed Checkout and Intent folded into open-mandate constraints (**H**).
4. `expiresAt` is **optional** in AP2 (`exp` optional on both mandate types); the #133 checker treats it as required — correct for RAP policy, but it must be reported as a RAP-imposed tightening, not an AP2 requirement (**H**).

## 2. A2A x402 extension (mandates into settlement)

Source: `spec/v0.1/spec.md` in [github.com/google-agentic-commerce/a2a-x402](https://github.com/google-agentic-commerce/a2a-x402) (raw read 2026-07-29, **H**). A2A v1.0 under Linux Foundation governance is baseline-sourced (Mar 2026, **M** — not re-verified this sweep).

- **Activation**: header `X-A2A-Extensions: https://github.com/google-a2a/a2a-x402/v0.1`, echoed by the server. The URI's `google-a2a` org differs from the repo's `google-agentic-commerce` home, and that hedge now resolves: `api.github.com/repos/google-a2a/a2a-x402` and `api.github.com/repos/google-agentic-commerce/a2a-x402` both return repository **id 999635940** with `full_name: google-agentic-commerce/a2a-x402` (both queried 2026-07-30, **H**). It is one repository behind an org-rename redirect, not an opaque non-resolving identifier — treat the header value as a stable version tag whose org segment is historical.
- **Metadata keys** on A2A task/message metadata: `x402.payment.status` (`payment-required` → `payment-submitted` → `payment-verified` → `payment-completed`, with `payment-rejected`/`payment-failed` branches), `x402.payment.required`, `x402.payment.payload`, `x402.payment.receipts` (**cumulative history array**), `x402.payment.error`.
- **Shapes**: `x402PaymentRequiredResponse{x402Version, accepts[]}`; `PaymentRequirements{scheme, network, asset, payTo, maxAmountRequired; optional resource, description, maxTimeoutSeconds, extra}`; `PaymentPayload{x402Version, network, scheme, payload}`; `x402SettleResponse{success, transaction, network, payer, optional errorReason}`. Error codes: `INSUFFICIENT_FUNDS`, `INVALID_SIGNATURE`, `EXPIRED_PAYMENT`, `DUPLICATE_NONCE`, `NETWORK_MISMATCH`, `INVALID_AMOUNT`, `SETTLEMENT_FAILED`.
- **How mandates ride**: the extension carries x402 payment evidence, not AP2 mandates as first-class objects — the client agent checks `PaymentRequirements` against the user's mandate and signs; mandate linkage to settlement is by the client's own binding (secondary corroboration: [typevar.dev a2a-x402 guide](https://typevar.dev/articles/google-agentic-commerce/a2a-x402), read 2026-07-29, **M**). There is **no mandate-hash field in the v0.1 shapes** — `PaymentPayload.payload` and `extra` are the only slots (**H** for the shapes; **M** for the practice). This is the gap RAP receipts already fill with `paymentEvidence.boundRequestId` + `delegatedAuthority.mandateId`.

## 3. FIDO agentic TWGs + Mastercard Verifiable Intent

**FIDO (watch-only)**: the 2026-04-28 [announcement](https://fidoalliance.org/fido-alliance-to-develop-standards-for-trusted-ai-agent-interactions/) (re-fetched HTTP 200, 248,564 bytes, tag-stripped and grepped 2026-07-30) describes a "newly formed Agentic Authentication Technical Working Group" — "chaired by members from CVS Health, Google and OpenAI and vice-chaired by members from Amazon, Google and Okta" — and places agent-initiated commerce work in the **Payments Technical Working Group**, "chaired by members from Mastercard and Visa". The two contributions are framed as inputs: "drawing from initial contributions from Google (AP2) and Mastercard (Verifiable Intent)", and "Technical contributions from Google and Mastercard are providing an initial foundation for these specifications", to be "reviewed and further developed through the FIDO Alliance’s collaborative standards process". All six strings verbatim, 1 hit each (**H**; note the page uses a typographic apostrophe in "Alliance’s" — the straight-quote form has 0 hits, which is the kind of detail that turns a grep-verified quote into an unverifiable one). The announcement calls only the Agentic Authentication group "newly formed" and refers to "its Payments Technical Working Group", so the Payments TWG reads as pre-existing and re-scoped rather than new (**M** — an inference from the modifier's placement, not a stated fact).

**No specification has been published by either TWG** — recorded here as an inference with its basis, not as a quotation, because the page makes no published-spec claim to quote. Basis: (i) the forward-looking framing above; (ii) the status sentence, verbatim, "Work has commenced within these workstreams, and the FIDO Alliance will provide reports as it progresses."; (iii) verified absence — the same fetch carries no specification, draft, or working-draft link for either contribution, and 0 hits for `Published Specifications` / `None yet`. Present language plus scoped absence → **H**. Corroboration [pymnts.com](https://www.pymnts.com/artificial-intelligence-2/2026/google-and-mastercard-contribute-agentic-commerce-standards-to-fido-alliance/) (**M**). Unknown, deliberately: FIDO's non-public TWG workspaces are outside this scope, so this says nothing about unpublished member drafts.

**Verifiable Intent (mappable today at credential-format level)**: [github.com/agent-intent/verifiable-intent](https://github.com/agent-intent/verifiable-intent/), `spec/{README,credential-format,constraints,security-model,design-rationale}.md` all fetched HTTP 200 and read 2026-07-30 (**H**). Status per correction (3) up front: **open specification, `0.1-draft`, Status Draft**, not an open standard. Licence Apache-2.0 and repository `created_at` `2026-03-05T09:41:38Z` via the GitHub repos API (id 1173370009, queried 2026-07-30) — that API read upgrades the launch-date claim from **M** to **H**, so the baseline's 2026-03-05 is confirmed against a primary record rather than press. `spec/README.md` also carries an internal document date of 2026-02-18, earlier than the repository, so read 2026-03-05 as publication, not authorship. Co-developed with Google; commitments from Fiserv, IBM, Checkout.com, Basis Theory, Getnet remain **M** (press only, not re-verified). Layered SD-JWT chain, RFC 7800 `cnf` binding each layer, and — repo README, verbatim — "Built on SD-JWT, JWS, JWK, and RFC 7800; no novel cryptography" (**H**):

- **L1** credential provider → user: identity claims, `cnf.jwk` = user device key; ~1-year life. The card claims are **profile-scoped, not generic L1 claims**: `spec/credential-format.md` states that "The claims `pan_last_four`, `scheme`, and `card_id` are defined by the Mastercard reference profile (`vct: "https://credentials.mastercard.com/card"`). Other credential profiles MAY define different required and optional claims appropriate to their payment instrument type." Only `iss`, `sub`, `iat`, `exp`, `vct`, `cnf`, `_sd_alg`, `_sd` are required regardless of profile (**H**). A non-card rail (an x402 stablecoin profile, say) would define its own L1 claim set, which is what makes an ADL-side mapping plausible at all.
- **L2** user → agent: checkout/payment constraints, `cnf.jwk` = agent key. **Two lifetimes, one per mode**, per the credential table in `spec/credential-format.md` §2 and its §7 lifetime table: L2 Immediate ~**15 minutes** (recommended and maximum both 15 min; `exp` "SHOULD be no more than 15 minutes from `iat`"), L2 Autonomous **24 hours – 30 days** (recommended default 30 days for consumer cases; maximum "MUST NOT exceed L1 `exp`"). Reporting only the 24h–30d figure, as an earlier draft did, silently drops the Immediate-mode profile (**H**).
- **L3** agent → network/merchant, **split L3a/L3b**: final values, `transaction_id`, `checkout_hash`; ~5-minute life (recommended 5 min, "MUST NOT exceed 1 hour"). Selective disclosure is role-scoped: networks see L3a, merchants see L3b.
- **Modes**: Immediate (L1+L2, no `cnf` delegation — user reviews final values, `typ: "kb-sd-jwt"`) vs Autonomous (L1+L2+L3, agent key bound, L2 `typ: "kb-sd-jwt+kb"`). Constraint vocabulary distinguishes machine-enforceable (amount, payee, merchant) from descriptive fields — and, separately, from **Network-Enforced Constraints** (§4 table (a), §5 item 4).
- **Vocabulary reuse is literal, not thematic**: VI does not merely share concepts with AP2, it reuses AP2's four `vct` strings unchanged as its own section headings — `spec/credential-format.md` §4.4.1 "Immediate Checkout Mandate (`vct: "mandate.checkout.1"`)", §4.4.2 "Immediate Payment Mandate (`vct: "mandate.payment.1"`)", §4.5.1 "Autonomous Checkout Mandate (`vct: "mandate.checkout.open.1"`)", §4.5.2 "Autonomous Payment Mandate (`vct: "mandate.payment.open.1"`)", with §5.5/§5.6 reusing the two closed values for L3b/L3a. Identical to the four values read from AP2's schemas in §1(b). `checkout_hash`, `transaction_id`, and `cnf` are likewise defined in VI's glossary with AP2-compatible semantics (`checkout_hash` on checkout mandates, "payment mandates carry the same hash as `transaction_id`"). Convergence is a shared credential type registry, not press framing — which is why one RAP ingestion rule can serve both (**H**).

## 4. ADL / RAP mapping tables

**ADL sources, corrected.** An earlier draft gave the authority field set as `{principal, spender, maxAmount, currency, expiry, revocation}` with `purpose`/`scope`/`rails` pushed out to the intent. That is wrong on three counts: there is no `expiry` field, `rails`/`purpose`/`scope` sit on the authority block itself, and `audit` was omitted entirely. Pasted verbatim from `$defs.paymentAuthority.required` in `specs/ADL-v0.2.schema.json` (read in this worktree 2026-07-30, **H**), all ten fields are required and `additionalProperties` is `false`:

```
["principal", "spender", "maxAmount", "currency", "rails", "purpose", "scope", "expiresAt", "revocation", "audit"]
```

Shapes that matter for the tables below, same file: `maxAmount` is a **decimal string** (`pattern` `^[0-9]+(\.[0-9]+)?$`), `currency` is an enum of `["USD", "USDC", "EUR", "GBP"]`, `rails` an enum array of `["x402-dry-run", "solana", "base", "stripe", "other-x402"]`, `expiresAt` a `Z`-suffixed second-precision timestamp pattern, `revocation` an object `{mode, path}` with `mode` ∈ `["operator", "policy-engine", "human-review"]`, and `audit` an object `{path, evidenceRef}`. The enclosing `$defs.paymentIntent` separately requires `["id", "direction", "maxAmount", "currency", "rails"]` and conditionally requires `purpose`/`scope`/`authority`/`requireReceipt`/`receiptRef`/`policyRefs` for `spend` and `refund` directions — so `maxAmount`/`currency`/`rails` appear at both levels, and the prose section `specs/ADL-v0.2.md` "Extension And Payment Authority Contract" (line 242) describes the contract the schema encodes. RAP side: `REQUIRED_LAYER_FIELDS["delegatedAuthority"] = (mandateId, principal, spender, payee, purpose, rail, maxAmount, expiresAt, auditRef)` (scripts/rap_receipt_validator.py, **H**).

### (a) AP2 v0.2 mandate claims ↔ ADL x402 authority block

| ADL/RAP authority field | AP2 v0.2 source | Rule / gap | Conf. |
|---|---|---|---|
| `principal` | SD-JWT issuer chain (credential provider → user); no named principal claim in the mandate body | Partial: principal is established by issuance + `cnf` chain, not a claim; ingest as the mandate issuer identity. | H |
| `spender` | `cnf` (JWK) on an open mandate | **Type mismatch**: ADL expects a party identifier; AP2 gives a key. Rule: spender = holder of the KB key; record a key thumbprint (RFC 7638) as the spender ref. | H |
| `payee` | `payee{id,name,website}` (closed) / `payment.allowed_payees` (open) | Direct (closed); set-valued on open mandates — ADL authority has one payee slot, so open mandates map to intent scope, not authority. | H |
| `purpose` | — (nearest: `checkout.line_items`; legacy `ap2.models` `natural_language_description`) | **No AP2 purpose claim.** Derive prose from constraints; lossy. | H |
| `rail` | — | **AP2 carries no rail.** Rail lives in x402 `PaymentRequirements.network`; `payment_instrument.type` is instrument, not rail. Cross-layer join required. | H |
| `maxAmount` | `payment.amount_range.max` / `payment.budget.max` (open); `payment_amount.amount` (closed) | Open constraints are the true cap; closed `payment_amount` is the actual charge — cap-vs-price distinction again (Pay.sh report §3). Ingest caps from open, actuals from closed. **Unit mismatch: AP2 amounts are integer minor units, ADL `maxAmount` is a decimal string** — `code/sdk/schemas/ap2/types/amount.json` (read 2026-07-30) types `amount` as `integer` with description "Amount in minor units, according to the ISO-4217 spec.", and `payment_mandate.json` spells out "integer minor units per ISO 4217, e.g., 27999 = $279.99"; ADL's pattern is `^[0-9]+(\.[0-9]+)?$`. Every amount crossing the boundary needs an explicit conversion keyed on the currency's ISO-4217 **minor-unit exponent** — 2 for USD per AP2's own worked example, but not 2 for every code — never a hard-coded ÷100. The exponent table is an external dependency this repo does not currently carry; that is an implementation prerequisite, not a solved detail. `payment.amount_range.max` is `integer` but `payment.budget.max` is `type: number`, so the two AP2 caps do not even share a unit convention; treat `budget.max` as unit-ambiguous until upstream clarifies. Additionally `payment.budget` and `payment.agent_recurrence` are **Network-Enforced Constraints** — declarable in a mandate, not evaluable by a stateless verifier (definition and scope in §5 item 4). | H |
| `currency` | `payment_amount.currency` (closed); `payment.amount_range.currency` / `payment.budget.currency` (open) | **Enum collision, one direction fatal.** AP2 types `currency` as "ISO-4217 3-letter alphabetic currency code of the payment" (`types/amount.json`) and the open-mandate constraints as "ISO4217 Alpha-3"; ADL's enum is `["USD","USDC","EUR","GBP"]` (`specs/ADL-v0.2.schema.json`). Two consequences. Inbound (AP2 → ADL): any AP2 currency outside the ADL enum — most of ISO-4217 — is unrepresentable, the `unfundable-currency-not-in-adl-enum` case already logged from the Pay.sh sweep. Outbound (ADL → AP2): **`USDC` cannot be expressed in AP2 at all** — it is not an ISO-4217 alpha code, so an AP2 mandate cannot denominate the stablecoin rail that ADL's `solana`/`base` rails imply. This is the sharpest structural limit found in the whole mapping: AP2's mandate layer is fiat-denominated by construction, and RAP's x402 lane is not. Report codes for §5 item 2: `ap2-cannot-express-usdc-currency` (outbound) and `ap2-minor-units-conversion-required` (unit conversion applied, with the exponent used recorded in the report). | H |

### Negative cases from #377, mapped

#377's scope names six negative cases; it groups "expired/revoked mandate" as one, but the two detect completely differently, so they get a row each — seven rows below. §1–§4 establish the fields that detect them, so the mapping is owed explicitly. "Stateless check" below means a check a report-only validator can perform on one submitted evidence bundle with no cross-request memory; two cases cannot be, and are marked report-only rather than dressed up.

| #377 negative case | Detecting AP2 v0.2 field | Stateless check | Verdict |
|---|---|---|---|
| Authorized resource but unauthorized payment | Absence of any `vct` ∈ {`mandate.payment.1`, `mandate.payment.open.1`} in the evidence bundle | Resource authorization (MCP/OAuth token, x402 `resource`) present while no Payment Mandate is present → **fail closed**. This is #377's named acceptance criterion; it is a presence check, so it belongs in the validator's required-layer logic, not in a scoring heuristic. | **Detectable, fail-closed** |
| Payment mandate without checkout mandate | Closed: required `transaction_id` (defined as the hash of `checkout_jwt`). Open: the `constraints` array's `"contains": {"$ref": "#/$defs/payment_reference"}`, i.e. a mandatory `payment.reference` carrying `conditional_transaction_id` | Closed — `transaction_id` present but no companion Checkout Mandate whose `checkout_hash` equals it → fail. Open — no `payment.reference` constraint → the mandate is schema-invalid before any RAP rule applies; present but with an unresolvable `conditional_transaction_id` → fail. AP2's schema does the structural half of this work for us. | **Detectable, fail-closed** |
| Checkout changed after approval | `checkout_hash` vs `checkout_jwt` (closed Checkout Mandate requires both) | Recompute the hash of `checkout_jwt` using `_sd_alg` (SHA-256 when absent) and compare to `checkout_hash`; separately require the Payment Mandate's `transaction_id` to equal that same value. Report-only mode does not verify the merchant's signature over `checkout_jwt`, so this catches mutation, not forgery — state that limit in the report. | **Detectable (mutation), fail-closed** |
| Agent-presented item differing from closed mandate | Closed: line items live *inside* `checkout_jwt` (the closed schema carries only `vct`/`checkout_jwt`/`checkout_hash`). Open — run AP2's own maximal-flow line-item match plus the merchant allow-list. Needs both the mandate and the presented cart in the same bundle; with only one, emit an insufficient-evidence code rather than a pass. | **Detectable when both sides are in evidence** |
| Expired mandate | `exp` (optional on all four schemas) + `payment.execution_date` `not_before`/`not_after` | Compare `exp` and the execution window to the receipt timestamp. Two of seven are report-only, and both for structural reasons rather than missing effort: AP2 has no revocation, and replay detection is a statefulness requirement, not a field mapping. Any deterministic checker built from this report should emit those two as explicit `report-only` outcomes so a freeze packet reader cannot mistake silence for a pass.

**Risks (explicit):**

- **Spec churn (H)**: AP2 restructured its mandate model once already (trio → open/closed pairs) within seven months, it now carries two mandate vocabularies in one repo tree (v0.2 schemas/SDK plus the legacy `ap2.models` trio, §1(b)/(c)), and FIDO's standards process will rework both contributions; a2a-x402 is v0.1. Pin every mapping row to `vct` values and read dates, and expect a second refresh when the FIDO TWGs publish. Note what this risk is *not*: the SDK does not lag the spec — an earlier draft of this report claimed it did, and §1(b) shows the generated models were emitted from the v0.2 schemas on the release day itself.
- **Scope boundary — Whispers of Wealth (H)**: per the baseline (arXiv 2601.22569), RAP receipts attest *authorized/paid/delivered/evaluated*, not *well-formed intent*. Mandate construction — whether the user's prompt was injected upstream of mandate signing — is out of scope for the validator, and the ingestion rule in (b) must say so: RAP verifies the mandate hash binding, never the mandate's wisdom.
- **Key-vs-identity mismatch (H)**: both AP2 and VI identify the spender by key (`cnf`), ADL by named party. The thumbprint rule works but breaks on key rotation; flag rotated-key mandates as new spenders until a registry-identity join (SATI report table (a)) exists.
- **No AP2 revocation (H)**: any ADL intent claiming an AP2-backed authority satisfies the required revocation mode only through RAP-side policy; validators must not report AP2 as providing one.
- **Fiat-denominated mandate layer vs stablecoin settlement (H)**: AP2 amounts are ISO-4217 integer minor units and its currency field is an ISO-4217 alpha code, so `USDC` — a value ADL's own enum permits — has no AP2 representation (table (a), `currency`). Any RAP flow that wants an AP2 mandate over an x402 stablecoin rail needs a declared convention for that, and until one exists the mandate layer and the settlement layer disagree about what money is.
- **Citation discipline (H)**: this report previously shipped a fabricated quotation on a headline finding (retraction in the correction notice). The failure mode is specific — a plausible-sounding string attributed to a page that was fetched but not grepped for that string. Anyone extending this report should grep before quoting and prefer a deep link to a domain; where the source cannot be re-read, paraphrase and downgrade rather than reconstruct.

# Agent Registry / SATI Identity-Reputation Compatibility Report

_Issue #378 (epic #386; feeds #392). Static research report — no code, no live invocation._
_Sources checked 2026-07-28/29 AEST. Baseline: research/2026-07-26-agent-payments-landscape-and-backlog-alignment.md §2 (Solana registry rows) and §4 (ERC-8004/AIP)._
_Confidence codes: **H** = primary source read directly; **M** = primary source partially readable or corroborated secondary; **L** = single secondary source or unverified convention._

**Correction notice up front**: the #378 reframe and baseline §2 state that the Foundation-endorsed Agent Registry and SATI are "both building reputation on Solana Attestation Service". That is **half right**, and the correction propagates to `docs/TRACKS.md` ("Registry/SATI attestation compatibility" bullet), which is amended alongside this report. SATI routes attestations through SAS and Light Protocol; the QuantuLabs `8004-solana` implementation behind the Foundation registry page **does not use SAS anywhere** — its reputation layer is its own SEAL v1 event-hash mechanism plus a maintained off-chain indexer (raw README, read 2026-07-28, **H**). The "dual-publish is cheap because of a shared SAS substrate" premise therefore does not hold as stated; dual-publishing means two distinct write paths (§6).

## 1. Foundation Agent Registry (solana.com/agent-registry + QuantuLabs/8004-solana)

**What the Foundation page actually is** ([solana.com/agent-registry](https://solana.com/agent-registry), read 2026-07-28, **H**): a marketing/portal page for an "open, onchain protocol that gives AI agents a verifiable identity, portable reputation, and trust infrastructure", framed as Identity / Reputation / Validation and "interoperable with ERC-8004 on Ethereum". It links an ecosystem, not one program: 8004.org (standards hub), 8004 Scan (explorer), 8004 Market (agent marketplace), developer docs at 8004.qnt.sh (Quantu), and — notably — the **SATI Dashboard**. The page presents the two registries as parts of one 8004 ecosystem, not competitors (**H** for the links; **M** for the intent reading). Registration is quoted at ~0.009 SOL (~$0.81) on the portal, while the repo fee table lists Register Agent at ~0.006 SOL — either way trivial — with minimal fees for feedback and wallet configuration (**H** for both figures, discrepancy noted).

**On-chain structure** (QuantuLabs/8004-solana README, raw read 2026-07-28, **H** unless noted):

- **Identity**: agents are **Metaplex Core NFTs** in a single collection; the agent identifier is the Core asset pubkey; metadata PDAs hang off it. Instructions: `register()`, `setAgentURI()`, `setMetadata()`, `setAgentWallet()`. So wallet address is a first-class mutable field, and the agent URI is expected to point at an ERC-8004-style registration file — the ERC-8004 registration JSON carries a `services[]` array (web, A2A, MCP, OASF, ENS, DID, email endpoints) and a `supportedTrust` field ([eips.ethereum.org/EIPS/eip-8004](https://eips.ethereum.org/EIPS/eip-8004), read 2026-07-29, **H** for the ERC; **M** that the Solana port inherits the file format by reference — the README does not restate the file schema). No A2A-card or MCP-endpoint fields exist on-chain; they live in the URI-referenced file.
- **Reputation**: `giveFeedback()` (score 0–100), `revokeFeedback()`, `appendResponse()` (intentionally permissionless). Feedback/revocation/response are **event-only**: the program computes a **SEAL v1** ("Solana Event Authenticity Layer") hash of the feedback parameters on-chain, and a maintained indexer (Supabase/Substreams) enforces consistency. Exact feedback field enumeration is deferred to `docs/SEAL.md`, not read this sweep — **Unknown** beyond the 0–100 score.
- **Validation**: **"Validation module archived for future upgrade"** — the TEE-attestation / staker-re-run / audit surface that ERC-8004's Validation Registry defines (`validationRequest()`/`validationResponse()` with `response` 0–100, `responseURI`, `responseHash`, `tag`; trust models "stake-secured re-execution, zkML verifiers or TEE oracles") **is not live on the Solana port** (**H**). This corrects the baseline §2 row, which listed all three registries without noting the gap. Sybil resistance is instead delegated to an external **ATOM Engine** (separate repo: HyperLogLog filtering, burst detection, five-tier trust classification) — off-chain, not a registry.
- **Program IDs / status**: devnet `8oo4J9tBB3Hna1jRQ3rWvJjojqM5DYTDJo5cejUuJy3C`, mainnet `8oo4dC4JvBLwy5tGgiH3WwK4B9PWxL9Z4XjA2jzkQMbQ`; mainnet deployment is evidenced by the address table and a documented reproducible binary hash (`5aeae715…c05a5c8`, dated 2026-03-04), though the README badge still reads Solana-Devnet and the roadmap's mainnet checkbox is unchecked — deployment real, self-description stale (**H** for the address/hash, **M** for production status).
- **Governance**: MIT license; "Only the program upgrade authority can call initialize"; no DAO/multisig/renouncement documented. Named completed audits: none found in the README (Kani formal checks are development-time only). Upgrade-authority holder and audit status: **Unknown** (**H** for the absence in the source read).

## 2. SATI (Cascade)

Sources: [docs.sati.cascade.fyi](https://docs.sati.cascade.fyi) (read 2026-07-28, **H**), sRFC #7 ([github.com/solana-foundation/SRFCs/discussions/7](https://github.com/solana-foundation/SRFCs/discussions/7), read 2026-07-28, **H**), [github.com/cascade-protocol/sati](https://github.com/cascade-protocol/sati) README (read 2026-07-28, **H**).

- **Program**: `satiRkxEiwZ51cv8PRu8UMzuaqeaNU9jABo6oAFMsLe` — **same address on mainnet and devnet** (**H**). ~500 lines, mostly CPIs. PDAs: `RegistryConfig`, `AgentIndex`, `SchemaConfig`. Instructions: `initialize()`, `register_agent()` (11 Token-2022 CPI calls), `register_schema_config()`, `create_attestation()`, `close_attestation()`.
- **Identity**: each agent is a **Token-2022 NFT** with extensions `MetadataPointer`, `TokenMetadata`, `GroupMemberPointer`, `TokenGroupMember`, and optionally `NonTransferable` (soulbound). Metadata stores CAIP-10 addresses, DIDs, **A2A endpoints, MCP URLs**; `uri` points at IPFS/HTTP; agent ID format `solana:<genesis-prefix>:<mint>` (**H**). Registration ~0.003 SOL, no protocol fee beyond rent.
- **Attestation storage is dual-routed** by `SchemaConfig.storage_type`: compressed via **Light Protocol** (ZK Compression, Photon indexing — ~$0.002 per feedback, ~$0.001 batched 5/tx) for high-volume feedback/validation, and **regular SAS attestations** (~0.002 SOL) where on-chain queryability matters (**H**). So even inside SATI, SAS proper carries only the low-volume schemas.
- **Universal base layout (131 bytes, verified on-chain)**: `layout_version` (1B), `task_ref` (32B, "CAIP-220 tx hash or task identifier"), `agent_mint` (32B), `counterparty` (32B), `outcome` (1B: 0=Negative, 1=Neutral, 2=Positive), `data_hash` (32B, "agent's blind commitment (keccak256 of request+response)"), `content_type` (1B enum: None/JSON/UTF-8/IPFS/Arweave/Encrypted) (**H**).
- **Five schemas**: `FeedbackV1` (compressed, dual-signature, non-closeable; optional JSON content with score 0–100, tags, message), `FeedbackPublicV1` (compressed, counterparty-signed, open submission — mirrors ERC-8004's post-Jan-2026 open model after `feedbackAuth` removal), `ValidationV1` (compressed, dual-signature; third-party validation — TEE, ZK-ML, re-execution), `ReputationScoreV3` (regular SAS, provider-computed aggregate, one per provider–agent pair, closeable), `DelegateV1` (regular SAS, hot/cold wallet separation, deterministic nonce) (**H**).
- **Blind feedback model**: the agent signs `interaction_hash = keccak256(schema || task_ref || data_hash)` when it serves the task; the counterparty signs a human-readable SIWS message after service. "Agent cannot refuse to participate in negative reviews because it has already committed by signing the interaction hash with its response" (**H**). This is structurally a commit-reveal: hash on-chain first, content optional/afterwards.
- **Governance/status**: `RegistryConfig.authority` is renounceable (transfer or set None = immutable) per the sRFC; whether mainnet authority has actually been renounced: **Unknown**. Apache-2.0. sRFC #7 is **Draft** (created 2025-11-11, updated 2026-02-11, 6 participants, no Foundation endorsement decision) (**H**). SDKs: `@cascade-fyi/sati-agent0-sdk`, `@cascade-fyi/sati-sdk`, `@cascade-fyi/compression-kit`. Audits: none named (**H** for absence).
- **Relation to the Foundation registry**: SATI claims 100% ERC-8004 *functional* compatibility — same registration file format, cross-chain identity via a `registrations[]` array and CAIP-2 (**H** for the claim, **M** for fidelity, not independently tested). Identity layers interoperate at the **file-format level**; on-chain, the two are disjoint programs with disjoint reputation write paths (Metaplex Core + SEAL events vs Token-2022 + SAS/Light attestations). The Foundation page linking the SATI Dashboard supports "complementary ecosystem" over "competitors", but nothing binds them programmatically (**M**).

## 3. Solana Attestation Service (the partial substrate)

Sources: [attest.solana.com](https://attest.solana.com) (read 2026-07-28, **H** for concept), [solana.com/docs/tools/attestations](https://solana.com/docs/tools/attestations) (read 2026-07-29, **H** for concept), Range/secondary corroboration (read 2026-07-29, **M**).

- **Account model**: three tiers — **Credential** (an attestation authority; holds authorized signers), **Schema** (structure and validation rules for attestations under a credential), **Attestation** (an individual claim conforming to a schema, created by an authorized signer). Roles: Issuer creates schemas and issues; Holder receives (push or pull); Verifier requests presentation (**H** for this model). Field-level layouts (expiry, nonce, exact account fields): **not obtained this sweep** — the docs pages fetched were conceptual and the deep-link paths 404'd; treat byte-level SAS layout as **Unknown** pending a repo-source read.
- **Who can attest**: only **authorized signers under a credential** — issuance is closed per-credential, not open (**H** for the model). This is the load-bearing fact for RAP: publishing SAS attestations means RAP (or its validator service) creates its own Credential + Schemas and controls the signer set. SATI's `create_attestation()` CPIs into SAS under SATI's schema configs (**M** — inferred from the sRFC architecture).
- **Program ID**: `22zoJMtdu4tQc2PzL74ZUT7FrwgB1Udec8DdW4yw4BdG` (**M** — search-corroborated secondary; not read from the program repo directly).
- **Cost/read paths**: regular SAS attestation ~0.002 SOL (rent; from SATI's numbers, **M** as a general SAS figure). Reads are standard account reads/indexers for regular attestations; SATI's compressed attestations require the **Photon** indexer (free tier per sRFC) (**H** for the dependency).

## 4. AIP — IETF draft-prakash-aip-00

Source: [datatracker.ietf.org/doc/draft-prakash-aip/](https://datatracker.ietf.org/doc/draft-prakash-aip/) (read 2026-07-28, **H**). Status: **individual submission, Informational, -00, dated 2026-03-27, expires 2026-09-28, not IETF-endorsed, no formal standing** — cite it as an I-D, never as "an IETF standard".

- **IBCT = Invocation-Bound Capability Token** (the baseline §4 abbreviation is this; note the expansion is *Invocation*-bound, not *Identity*-bound). One artifact binding who authorized, through which delegation chain, with what constraints per hop, and what outcome resulted.
- **Compact mode (JWT/EdDSA-Ed25519)**: single-hop only; claims: issuer, subject, `scope[]`, **budget ceiling (USD)**, max delegation depth (0 = no further delegation), iat/exp; lifetime should be <1h.
- **Chained mode (Biscuit)**: append-only blocks. Block 0 (authority): root identity, initial capabilities, budget, max_depth, expiration. Blocks 1..N-1 (delegation): delegator, delegate, attenuated capabilities as Datalog facts, budget attenuation, **mandatory non-empty `context`**. Scope can only narrow (tools, budget, domains, expiry); wildcards can specialize, values cannot re-widen. Optional final **completion block** signed by the executing agent: status, SHA-256 result hash, verification trust level — an audit record inside the token itself.
- **Identity/discovery**: `aip:web:<domain>/<path>` resolved at `https://<domain>/.well-known/aip/<path>.json`, or self-certifying `aip:key:ed25519:<multibase>`. IANA requests: `AIP` HTTP auth scheme, `aip` well-known suffix, `application/aip+jwt`. Token-by-reference via `X-AIP-Token-Ref` for tokens >4KB.
- **Naming collision warning (H)**: at least three *other* active I-Ds are also titled "Agent Identity Protocol": `draft-singla-agent-identity-protocol` (at -03), `draft-fane-opena2a-aip-00`, `draft-aip-agent-identity-protocol-00`. All RAP/ADL docs citing "AIP" must pin `draft-prakash-aip-00` explicitly, mirroring the ACP disambiguation rule from the baseline. The SATI sRFC thread separately references a "did:aip" W3C DID Method sRFC (#11) — whether that AIP is this AIP is **unverified (L)**; do not conflate without reading sRFC #11.

### (b) RAP receipt-verified reputation ↔ registry feedback + SAS attestations

The strongest finding of this sweep: **SATI's blind-feedback layout is nearly isomorphic to RAP's commit-reveal receipt model** — `data_hash` is an on-chain commitment (keccak256 of request+response) made *before* content is revealed, and the agent's signature over `interaction_hash` is exactly RAP's "provider committed to this delivery" event.

| SATI/8004 field | RAP receipt source (validator layer.field) | Rule / gap | Conf. |
|---|---|---|---|
| `task_ref` (32B) | `paymentEvidence.boundRequestId` / `replayIdempotency.receiptId` | Map via hash: RAP IDs are strings; `task_ref` is 32 bytes ("CAIP-220 tx hash or task identifier") — publish `sha256(receiptId)` or the settlement signature. | H |
| `agent_mint` | — (`serviceOutcome.agentId` is a string) | Requires the agent to hold a registry identity; ADL/RAP has no mint field today — depends on the (a) pointer work. | H |
| `counterparty` | `delegatedAuthority.principal` or `paymentEvidence`'s payer side | Direct once the payer has a pubkey identity. | M |
| `outcome` (0/1/2) | `serviceOutcome.status` + `evalEvidence.status` | **Lossy**: 8 ADL signal types (taskCompleted, evalPassed, receiptVerified, budgetRespected, toolPolicyRespected, humanApproved, disputeOpened, refundIssued) collapse to a tri-state. Recover fidelity via content JSON `tags` (SATI) / `tag1`,`tag2` (ERC-8004) — also satisfies skill-conditional reputation (arXiv 2606.14200): tag the ADL capability, never a single scalar. | H |
| `data_hash` | `serviceOutcome.requestHash` + `responseHash` | **Algorithm mismatch to resolve**: SATI pins `keccak256(request‖response)` as one hash; RAP carries two separate hashes with no pinned algorithm in the validator (fields are plain strings). Dual-publish needs a deterministic derivation rule, e.g. `data_hash = keccak256(requestHash ‖ responseHash)`, written into the RAP receipt spec. | H |
| `content_type` + optional content (score/tags/message; IPFS/Arweave/Encrypted) | reveal-phase payload | **Commit-reveal fit**: commit = attestation with `data_hash` and `content_type: None` (or `Encrypted`); reveal = content published matching the hash. What stays committed-only: amounts, payee, payer identity — the base layout has **no amount field**, which suits `privacyAccounting` (money detail stays in the RAP receipt; the public attestation proves the event). | H |
| ERC-8004 off-chain feedback file `proofOfPayment` (chain ID, tx hash, addresses) | `settlementProgramProof` (cluster, signature, mint, programId, confirmationStatus, payer, payee, amount) | Direct enrichment — RAP receipts are exactly the "x402 payment-proof schema" ERC-8004's v2 track wants (baseline §4). On the Solana port this lands in the SEAL-hashed indexer-side file, format unread (**Unknown** fields). | M |
| `giveFeedback()` score 0–100 (8004-solana) | `evalEvidence` + `serviceOutcome` | Publishable, but full field list is behind docs/SEAL.md (unread) and legibility depends on their maintained indexer. | M |
| `ReputationScoreV3` (provider aggregate, one per provider–agent) | — | RAP-as-provider could publish its receipt-verified aggregate here — a differentiated "receipt-backed score" product. Collusion caveat in §6. | M |

|---|---|---|---|

## 6. Recommendation block

**For reddiagent-lab (spec side, feeds #392):**

1. A mapping spec `specs/REGISTRY-ATTESTATION-MAPPING-v0.1.md` (or #392's chosen name) normatively pinning: the `extensions.identity` pointer schema from table (a) (registry kind + CAIP-2 chain + asset/mint + registration-file URI + optional AIP identifier), the `data_hash` derivation rule, the signal→outcome+tags collapse table from (b), and the evalEvidence→ValidationV1 projection from (c).
2. A report-only script (`scripts/registry_attestation_compatibility.py`, MAF report contract: `runtimeExecutionAllowed`/`networkAccess`/`paymentAccess`/`mcpInvocation` all false) that takes an ADL doc plus a locally supplied RAP receipt fixture and emits: derivable attestation stubs (SATI 131-byte base layout fields), loss codes (`adl-no-registry-pointer`, `adl-no-wallet-address`, `adl-no-served-endpoint`, `signals-collapsed-to-outcome`), and refusals for anything requiring a live registry read. It validates *shape*, it never fetches.
3. Do not add wallet/A2A-endpoint *values* to ADL v0.2 — keep them registry-side; ADL carries pointers only (consistent with the Pay.sh report's §5 verdict).

**For the protocol repo (integration order):** integrate **SATI first**. Reasons: (i) same program ID on mainnet and devnet — the devnet gate (rung 3) and Surfpool mainnet-fork rehearsal (#394, rung 2) exercise the *same* address; (ii) the blind-commitment design is structurally the RAP commit-reveal model, so dual-signature `FeedbackV1` gives RAP receipts an on-chain landing spot with minimal impedance; (iii) costs are trivial (~0.003 SOL registration, ~$0.002/attestation); (iv) Apache-2.0 with a published sRFC. Then dual-publish to **8004-solana second**: identity dual-registration is cheap and mostly a file-format exercise (same ERC-8004 registration JSON; ~0.012 SOL combined), but reputation dual-publish is **two write paths, not one** — a `giveFeedback()` instruction whose events are only as legible as Quantu's maintained indexer, plus the SATI attestation. Budget it as a second integration, not a free rider on SAS. Ethereum-side ERC-8004 publishing stays a later parity target (baseline §4).

**Risks (explicit):**

- **Registry immaturity (H)**: ERC-8004 is still Draft; sRFC #7 is still Draft with 6 participants and no Foundation endorsement decision; ERC-8004 adoption is measured as concentrated and shallow (~10k agents, arXiv 2606.12128). Neither Solana registry has a named completed audit in the sources read.
- **Upgrade-authority centralization (H for the facts, M for severity)**: 8004-solana is single-upgrade-authority with no governance documentation; SATI's authority is renounceable by design but its current mainnet state is unverified. Until verified, treat both registries' state as mutable-by-operator and keep RAP's own receipts as the root of trust, with registry entries as *published projections*.
- **Attestation spam and collusion (H)**: `FeedbackPublicV1` and post-Jan-2026 ERC-8004 are open-submission — sybil feedback is a design-accepted cost pushed to off-chain scoring (ATOM on the Quantu side, providers on the SATI side). The **AgentReputation collusion model (arXiv 2605.00073)** applies directly to `ReputationScoreV3`: provider-computed aggregates are single-verifier scores, and verifier–agent collusion is undetectable on-chain. RAP's differentiation is publishing only **receipt-verified** events (dual-signed, settlement-bound) into these open pools — and consumers must weight by attestation provenance, not count.
- **Indexer dependencies (H)**: compressed SATI attestations are readable only through Photon; 8004-solana feedback is readable only through Quantu's indexer. Both are availability and integrity dependencies outside the chain's trust model; the SEAL/ZK-compression hashes bound the integrity risk but not the availability risk.
- **AIP is a -00 individual I-D (H)**: expires 2026-09-28; three same-named drafts in flight. Treat as a portability target and vocabulary source for `delegatedAuthority`, not a dependency.
